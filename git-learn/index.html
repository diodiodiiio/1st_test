Git とは？

バージョン管理システムの基本概念

VCS バージョン管理システム

Git は分散型バージョン管理システム (DVCS) です。 ファイルの変更履歴を記録・追跡し、過去の状態に戻したり、複数人での並行作業を管理したりできます。

中央集権型 (SVN など)

[開発者A] ─┐ [開発者B] ─┼─▶ [中央サーバー] [開発者C] ─┘ 履歴はサーバーだけに存在

サーバーが落ちると作業できない。履歴の参照にもネットワークが必要。

分散型 (Git)

[開発者A] ◀──▶ [リモート] ↕ ↕ [開発者B] ◀──▶ [開発者C] 全員が完全な履歴を持つ

オフラインでも作業可能。リモートがなくてもローカルで完結する。

Git が管理するもの

Git はファイルのスナップショットを保存します。変更差分ではなく、コミット時点のファイル全体の状態（スナップショット）をリポジトリに記録します。

コミット1 コミット2 コミット3 │ │ │ ▼ ▼ ▼ [A=1] [A=1] [A=3] ← Aが変更 [B=2] [B=5] [B=5] ← Bが変更 [C=3] [C=3] [C=3] 変更なし→前を参照
リポジトリ (repository / repo)とは、Git がプロジェクトの全履歴を保存しているデータベースのことです。 ローカルの .git/ フォルダがそれにあたります。

3つのエリア

Git の最重要概念 — ファイルはどこにいるのか

Gitの3エリアとその流れ

┌─────────────────┐ git add ┌───────────────┐ git commit ┌───────────────┐ │ 作業ツリー │ ──────────▶ │ ステージング │ ─────────────▶ │ リポジトリ │ │ Working Tree │ │ Staging Area │ │ Repository │ │ │ │ (Index) │ │ (.git/) │ │ 実際に編集する │ │ 次のコミットに │ │ コミット履歴 │ │ ファイル群 │ ◀────────── │ 含める変更を │ │ が保存される │ │ │ git restore │ 一時保管 │ │ │ └─────────────────┘ └───────────────┘ └───────────────┘ ▲ │ └──────────────────────── git checkout / restore ─────────────────┘

1 作業ツリー (Working Tree)

実際に編集しているファイルが存在する場所。エディタで変更を加えるとここが変わります。 Git はこのエリアの変更を自動的には記録しません。

git status # 状態確認 # → "modified: app.js" と表示される

2 ステージングエリア (Index)

「次のコミットに含めたい変更」を一時的に登録する場所。 複数のファイルを変更しても、選んでコミットできます。

git add app.js # 特定ファイル git add -p # 変更を部分選択

3 リポジトリ (.git/)

コミットされた履歴が永続的に保存される場所。git commit を実行すると、 ステージングエリアの内容が新しいコミットとしてリポジトリに追加されます。

よくある混乱： ファイルを保存しただけではGitは何も記録しません。 git add → git commit の2ステップが必要です。

ファイルのライフサイクル

Untracked ──── git add ────▶ Staged ──── git commit ────▶ Unmodified ▲ │ │ git rm ファイル編集 │ │ └───── Untracked ◀── git restore ◀── Modified ◀───────────┘

Untracked: Gitが管理していない新規ファイル
Staged: ステージ済み（次のコミット対象）
Unmodified: コミット済みで変更なし
Modified: コミット済みだが変更あり

コミット (Commit)

変更のスナップショットと履歴の構造

コミットとは

コミットはプロジェクトのある時点のスナップショットです。 各コミットは固有のSHA-1ハッシュ（例: a3f1b2c）を持ちます。

コミットの中身: ┌──────────────────────────────────────┐ │ hash : a3f1b2c9d4e8... │ │ author : Alice <alice@example.com> │ │ date : 2024-01-15 10:30:00 │ │ message : "ログイン機能を追加" │ │ parent : 7e2c4a1... (前のコミット) │ │ tree : <ファイルのスナップショット> │ └──────────────────────────────────────┘

コミット履歴はリンクリスト

古い ←───────────────────────────────── 新しい [c1: 初期] ←── [c2: 修正] ←── [c3: 追加] ←── [c4: リファクタ] ▲ HEAD (現在地点)

各コミットは親コミットへの参照を持ちます。これにより「どこから変更が加えられたか」を追跡できます。

基本コマンド

git add . # 全変更をステージ git commit -m "メッセージ" git commit -am "追跡済みを一括" git log # 履歴を見る git log --oneline # 1行表示 git show a3f1b2c # 特定コミット確認

良いコミットメッセージ

# ✅ 良い例 "ユーザー認証にJWTトークンを追加" "fix: パスワードリセット時のバグ修正" "docs: READMEにセットアップ手順を追加" # ❌ 悪い例 "修正" "wip" "いろいろ変えた"
ベストプラクティス： 1つのコミットには1つの目的の変更だけ含めましょう。「ログイン機能を追加 + デザイン変更 + バグ修正」を1コミットにまとめるのは避けましょう。

ブランチ (Branch)

開発の流れを分岐させる仕組み

ブランチとは

ブランチは特定のコミットを指す軽量なポインタです。 新機能の開発やバグ修正を main ブランチに影響なく進められます。

feature/login ▼ main: [c1] ←── [c2] ←── [c3] ←── [c5] ← 新機能コミット └────────── [c4] ←── [c6] ← バグ修正 ▲ fix/bug-123

ブランチの操作

git branch # 一覧 git branch feature/x # 作成 git switch feature/x # 移動 git switch -c feature/x # 作成+移動 git branch -d feature/x # 削除

ブランチの命名規則（例）

main # 本番環境 develop # 開発統合ブランチ feature/login # 新機能 fix/issue-42 # バグ修正 hotfix/security # 緊急修正 release/v1.2 # リリース準備

Git Flow（代表的なブランチ戦略）

main ●────────────────────────────────────────● 本番リリース \ / develop ●──────────●──────────────────────●── 開発統合 \ / \ / feature ●──────● ●──────────────────● 機能開発 \ / release ●────────────● リリース準備 \ hotfix ●──● 緊急修正
ブランチの切り替え (git switch) は非常に高速です。 Git はファイルをコピーするのではなく、HEADポインタを変更するだけだからです。

マージ (Merge)

ブランチの変更を統合する方法

FF Fast-Forward マージ

マージ前: main: [c1] ←── [c2] └── [c3] ←── [c4] ▲ feature マージ後 (ff): main: [c1] ←── [c2] ←── [c3] ←── [c4] ▲ main, feature

枝分かれがない場合、mainポインタを前に進めるだけ。 マージコミットは作成されません。

3-way No-FF マージ

マージ前: main: [c1] ←── [c2] ←── [c5] └── [c3] ←── [c4] ▲ feature マージ後: main: [c1] ←── [c2] ←── [c5] ←── [c6★] └── [c3] ←── [c4] ───┘ マージコミット

3つのコミット（共通祖先・各ブランチ先端）を使って統合。 マージコミットが作成されます。

マージのコマンド

git switch main # 統合先に移動 git merge feature/login # ブランチを統合 git merge --no-ff feature/login # 必ずマージコミット作成 git merge --abort # コンフリクト時に中断

コンフリクト (Conflict) の解決

同じ行を異なるブランチで編集するとコンフリクトが発生します。

ファイル内にコンフリクトマーカーが挿入される: ┌─────────────────────────────────────┐ │ <<<<<<< HEAD (現在のブランチ) │ │ console.log("ようこそ！"); │ │ ======= │ │ console.log("Welcome!"); │ │ >>>>>>> feature/i18n (統合するブランチ) │ └─────────────────────────────────────┘
# 解決手順: # 1. エディタでマーカーを含む行を手動で編集 git add conflicted-file.js # 2. 解決済みとしてマーク git commit # 3. マージコミットを完了
コンフリクトは怖くありません。Git がどちらの変更を残すべきか判断できないだけです。 マーカー行を消して正しい内容にするだけで解決できます。

リベース (Rebase)

コミット履歴を書き換えてきれいにする

リベースとは

ブランチのコミットを別のコミットの上に付け替える操作です。 マージとは異なり、コミット履歴が一直線になります。

リベース前: main: [A] ←── [B] ←── [C] └── [D] ←── [E] ▲ feature git rebase main (featureブランチで実行): main: [A] ←── [B] ←── [C] └── [D'] ←── [E'] ▲ feature ※ D', E' は D, E の内容は同じだがハッシュが変わる

マージとの比較

マージ: A ← B ← C ← M (マージコミット) ↑ ↗ D ← E リベース: A ← B ← C ← D' ← E' 履歴が一直線でクリーン

コマンド

git switch feature git rebase main # mainの上に付け替え # インタラクティブリベース git rebase -i HEAD~3 # 直近3コミットを整理 # コンフリクト時 git rebase --continue git rebase --abort

インタラクティブリベースで履歴を整理

git rebase -i HEAD~4 # エディタが開く # エディタ内での操作: pick a3f1b2c 機能Aを追加 squash 7e2c4a1 機能Aの修正 # ↑と1つにまとめる reword 9b8d3f2 誤字修正 # メッセージを書き直す drop c4a1e5d 不要なコミット # 削除する
黄金律： すでにリモートに push したコミットをリベースしてはいけません。 他の開発者の履歴と矛盾が生じます。リベースはローカルのみ、または自分だけが使うブランチに限定しましょう。

リモートとの連携

GitHub などのリモートリポジトリと同期する

リモートリポジトリの概念

ローカル リモート (GitHub等) ───────────────── ───────────────── main ──── git push ────▶ origin/main feature ──── git push ────▶ origin/feature ◀─── git fetch ─── origin/* ローカルのorigin/* は サーバー上の リモートの状態の"鏡" 実際のブランチ

主なコマンド

# リモートを登録 git remote add origin <URL> # 変更を送信 git push origin main git push -u origin feature # リモートの情報を取得 git fetch origin git pull origin main # リポジトリをコピー git clone <URL>

fetch vs pull

git fetch: リモートの変更を取得するが 作業ツリーは変更しない origin/main だけ更新 git pull: fetch + merge を実行 = git fetch && git merge 作業ツリーが更新される

安全なのは fetch して内容を確認してから merge する方法です。

clone の仕組み

git clone https://github.com/user/repo.git 実行されること: 1. .git/ ディレクトリ（リポジトリ全体）をコピー 2. origin という名前でリモートURLを登録 3. デフォルトブランチ（main）をチェックアウト 4. origin/main などのリモート追跡ブランチを設定

上流ブランチ (upstream / tracking branch)

ローカルブランチとリモートブランチを紐付けることで、git push/git pull を引数なしで使えます。

git push -u origin main # -u で上流を設定 # 以降は git push だけで OK git branch -vv # 上流ブランチを確認

HEAD・参照

Git がどこを「現在地」と認識しているか

HEAD とは

HEAD は「現在チェックアウトしているコミット」を指すポインタです。 通常はブランチを指し、ブランチがコミットを指します。

HEAD ──▶ main ──▶ [c4: 最新コミット] ↑ ここが現在地

通常状態

HEAD → main → c4 git commit すると: HEAD → main → c5 (新コミット) ブランチも自動で前進する

Detached HEAD

git checkout a3f1b2c (古いコミット) HEAD → a3f1b2c ← ブランチを経由しない！ この状態でコミットしても ブランチが更新されない

過去の状態を見るだけなら問題なし。作業するならブランチを作成しましょう。

相対参照

ハッシュを覚えなくてもコミットを参照できます。

HEAD # 現在のコミット HEAD~1 # 1つ前のコミット (HEAD^ と同じ) HEAD~3 # 3つ前のコミット main~2 # mainの2つ前 # 使用例 git show HEAD~1 # 1つ前を確認 git diff HEAD~2 HEAD # 2コミット分の差分 git reset HEAD~1 # 直前のコミットを取り消し

タグ (Tag)

タグは特定のコミットに付ける名前付きの永続的ポインタです。リリースバージョンの管理によく使います。

git tag v1.0.0 # 軽量タグ git tag -a v1.0.0 -m "リリース" # 注釈付きタグ git push origin --tags # タグをプッシュ
